# DeepSeek V4.1 Flash

DeepSeek V4.1 Flash (`general.architecture = deepseek41`) runs on the
DeepSeek4 backend. This page is for engineers picking up the port: what is
implemented, how to build and run it with the routed experts streamed from
SSD, what it measures today, and what is still missing. For everything the
two models share (hyper-connections, MoE placement, the hybrid expert tier,
reasoning effort, tool calls) see [DS4.md](DS4.md).

## Status

The model answers coherently on one R9700 with most routed experts streamed
from NVMe, or with the experts split across the R9700, the Strix Halo and
NVMe, through the host hyper-connection paths, with dense attention over
the compressed rows and without the Engram memory. Of the V4 fast paths,
DSpark speculative decoding, the fused whole-model graph (decode and verify)
and paged concurrent serving handle V4.1, with greedy output bit-identical
to plain decode and each concurrent sequence bit-identical to the same
request alone; layer-major prefill, layer split and vision do not yet, and
the backend refuses them rather than produce wrong tokens.

| Piece | State |
| --- | --- |
| Loader: `deepseek41` keys (llama.cpp PR #28696 and DwarfStar dialects), source layers, candidates, Engram constants | done |
| Compressed caches owned by kv source layers and read by the layers after them | done (contiguous and paged cache, snapshots) |
| Ratio-2 compressor (pooled, no APE) and ratio-1 compressor (per-token latent) | done |
| Index keys from the latent at kv sources that are index sources | written, not scored |
| No per-head query norm; staggered hyper-connection pre-mix; head collapse | done on the host HC paths |
| 384 routed experts, `moe_intermediate_size` 2304, hot/cold placement and SSD streaming | done |
| Three expert owners (R9700, Strix via in-process TP, SSD) from a placement file; router bias; protected experts | done (host routing) |
| ROCMFP2S weights (sign-flip bit in the ROCMFP2 scale byte) | done (HIP kernels and CPU reference) |
| Engram hashing and table read | done and tested, not wired into the forward pass |
| Engram apply (ggml subgraph) | written, not wired, not yet validated |
| Indexer top-k (512) shared by the readers of an index source | missing: attention is dense |
| Candidate block pre-selection (layer 20, 2048 blocks of 8) | missing (an exact no-op below 16,384 compressed rows) |
| DSpark drafter (converter, loader, draft graph) and speculative decoding | done (host HC path and fused graph, bit-identical to plain decode) |
| Fused hybrid decode and verify with the streamed experts as a third owner | done (see below) |
| Paged concurrent serving | done (default expert-owner kernels) |
| Expert promotion to the R9700 | experimental, off by default |
| q5 verify, layer-major prefill, layer split, vision | refused for V4.1 |

Dense attention computes what the reference computes (up to F16 cache
rounding) while every query sees at most 512 compressed rows, that is up to
about 1,024 tokens of context on the ratio-2 layers and 512 on the ratio-1
layers. Beyond that the reference attends to its indexer's top 512 rows, so
long-context output drifts until the indexer is wired. Without Engram, layers 1 and 14 run without their
n-gram memory; short answers are coherent (below), but this is not the
reference model yet.

## What changes from V4 Flash

| | V4 Flash (0731) | V4.1 Flash |
| --- | --- | --- |
| Layers, hidden | 43 (+3 MTP), 4096 | 40 (+3 DSpark), 5120 |
| Routed experts | 256 / top-6, ffn 2048, 3 hash-routed layers | 384 / top-6, ffn 2304, no hash routing |
| Compress ratios | 0, 0, then 4 and 128 alternating | 0, 0, then 2 (layers 2-19), 1 (20-39) |
| Compressed rows | every compressing layer owns its own | only kv sources 2, 8, 14, 20 run a compressor; the layers after a source read its rows |
| Indexer | own compressor at every ratio-4 layer | index sources 2, 8, 14, 20, 24, 28, 32, 36; keys projected from the compressed latent |
| Query norm | per-head RMS norm after `wq_b` | none |
| Hyper-connection pre-mix | each sub-block uses its own pre coefficients; `output_hc_*` for the head | staggered: a sub-block uses the previous one's, the head the last FFN's; mixes normalized with `norm_eps` |
| Engram | none | layers 1 and 14, 24 hashed rows per token per layer, tables of 384M rows x 264 bytes |

The loader turns the forward-pass differences into rules on
`DeepSeek4Weights` (`attn_q_head_norm`, `hc_staggered_pre`,
`shared_comp_cache`, `kv_src` / `idx_src`), so the graph code tests
behaviors, not architecture names.

## Build

Same build as V4, for example on an R9700 + Strix Halo machine:

```bash
cmake -S server -B server/build-hip \
  -DCMAKE_BUILD_TYPE=Release \
  -DLUCE_GPU_BACKEND=hip \
  -DLUCE_HIP_ARCHITECTURES='gfx1151;gfx1201' \
  -DCMAKE_HIP_ARCHITECTURES='gfx1151;gfx1201'
cmake --build server/build-hip -j --target luce_server
```

Unit tests that cover the port (with `-DLUCE_TESTS=ON`): `test_ds4_engram`
(hash and row decode against golden vectors from a port of the reference),
`test_paged_kv_pool` (includes the shared-cache geometry and paged plan) and
`test_rocmfpx` (ROCMFP2S sign flip).

## Running with cold experts streamed from SSD

The ROCMFP2S build (`DeepSeek-V4.1-Flash-ROCMFP2S.gguf`, 383 GB: 158 GiB of
routed experts, 8 GiB of dense weights, 189 GiB of embedded Engram tables)
does not fit in GPU memory plus host RAM on a 32 GB GPU + 64 GiB carve +
61 GB RAM box. The hybrid expert tier handles it without extra flags: dense
weights and the hottest experts go to the target GPU, and every other expert
stays in the GGUF memory map. Each MoE step streams the cold experts it
selected through a pinned staging buffer into GPU scratch and computes them
there (`src/common/moe_hybrid_stream.cpp`); the OS page cache keeps the
recently used ones in host RAM and the rest come from NVMe. The Engram tables
are never mapped.

```bash
export LUCE_EXPERT_BUDGET_MB=6000        # hot experts on the R9700
export ROCBLAS_USE_HIPBLASLT=0 GPU_MAX_HW_QUEUES=8
./server/build-hip/luce_server /path/to/DeepSeek-V4.1-Flash-ROCMFP2S.gguf \
  --host 127.0.0.1 --port 8080 --model-name deepseek-v41-flash \
  --target-device hip:0 --max-ctx 4096 --chunk 1024 --max-tokens 256 \
  --prefix-cache-slots 0 --prefill-cache-slots 0
```

Leave the default `--ds4-prefill exact`, and do not set
`--ds4-fused-decode` or a layer split: the backend refuses them for V4.1.
The fused graph, speculative decoding and paged serving are described
below. The load log shows the resolved sharing and the
placement:

```
[deepseek4] compress_ratios=[0, 0, 2, ..., 1] kv_sources=[2, 8, 14, 20] (declared) index_sources=[2, 8, 14, 20, 24, 28, 32, 36]
[deepseek4] engram: layers=[1, 14] heads=8 key_len=256 max_ngram=4 rows=[384006168, 384016682], 2 table(s) embedded in the GGUF (not mapped)
[deepseek4] cold-expert stream engine ready: pinned=... scratch=...
[deepseek4] hybrid experts ready: hot=... cold=... cold_backend=cpu
[deepseek4] deepseek41: the Engram layers run without their n-gram memory and compressed attention is dense
```

## Three expert owners: R9700, Strix Halo and SSD

The Lucebox layout splits the routed experts three ways: the R9700 owns a hot
stack, the Strix Halo owns a second stack through the in-process expert
parallel path (`LUCE_DS4_MOE_TP`, see DS4.md), and every other expert is
streamed from NVMe as above. By default the Strix stack is the complement of
the hot set, which does not fit for V4.1 (143 GiB against a 64 GiB carve);
`--ds4-expert-placement` makes the split explicit.

```bash
export LUCE_DS4_MOE_TP=1 LUCE_DS4_MOE_TP_INPROC=1 LUCE_DS4_MOE_TP_GPU=1
export LUCE_EXPERT_BUDGET_MB=18000              # R9700 (primary) experts
export LUCE_EXPERT_SECONDARY_BUDGET_MB=56000    # Strix (secondary) experts
export ROCBLAS_USE_HIPBLASLT=0 GPU_MAX_HW_QUEUES=8
./server/build-hip/luce_server /path/to/DeepSeek-V4.1-Flash-ROCMFP2S.gguf \
  --host 127.0.0.1 --port 8080 --model-name deepseek-v41-flash \
  --target-device hip:0 --peer-access --max-ctx 4096 --chunk 1024 \
  --prefix-cache-slots 0 --prefill-cache-slots 0 \
  --ds4-expert-placement placement.json \
  --ds4-router-bias router_bias_40x384_f32.bin \
  --ds4-protected-experts protected_experts.json
```

- `--ds4-expert-placement FILE`: JSON `{"owners": [...]}` with one entry per
  expert, index `layer * n_expert + expert` (15,360 for V4.1), each
  `"primary"`, `"secondary"` or `"stream"`. The file is a ranking, not a
  promise: each device keeps what fits its byte budget and demotes the rest
  one tier (primary to secondary, secondary to stream). The primary budget is
  what the default placement would spend (`LUCE_EXPERT_BUDGET_MB`, or the
  free VRAM after dense weights and KV); the secondary budget is
  `LUCE_EXPERT_SECONDARY_BUDGET_MB`, or the secondary device's free memory
  minus 4 GiB. Keep it inside the Strix carve: past it, allocations spill
  into host memory that the SSD tier needs as page cache. Demotions take
  the least-used experts first when `LUCE_DS4_HOTNESS_CSV` points to a
  routing profile (written by `LUCE_DS4_ROUTING_STATS_OUT`), otherwise they
  are spread evenly across layers. Without `LUCE_DS4_HOTNESS_CSV`, an
  existing `LUCE_DS4_ROUTING_STATS_OUT` file ranks them instead, and the
  server resumes counting into it (saved after every request and at
  shutdown), so the placement learns from what it serves across restarts. Without in-process TP the secondary tier
  is empty and its experts stream. The load log prints the final tiers:

  ```
  [deepseek4] expert ownership: primary 1680 experts 17.30 GiB (budget 17.30 GiB), secondary 5309 experts 54.68 GiB (budget 54.69 GiB), streamed 8371 experts 86.22 GiB
  ```
- `--ds4-router-bias FILE`: raw little-endian f32 `[n_layer][n_expert]`,
  added once at load to each layer's selection bias (`exp_probs_b`), so it
  moves which experts are selected, not their mixing weights, and costs
  nothing per token.
- `--ds4-protected-experts FILE`: JSON `{"<layer>": [expert ids]}`. A token
  whose native top-k (the selection without the router bias) contains a
  protected expert keeps its native selection; protected experts are always
  owned by the primary GPU, whatever the placement file says. The rule runs
  in the host routing of the hybrid expert tier
  (`ds4_select_routed_experts` in `deepseek4_graph.cpp`): one extra top-k
  over 384 scores per token and layer when a router bias is loaded, nothing
  otherwise. The GPU routing graph of a fully resident model does not
  implement it, so the backend refuses the flag there.

Every request logs where its routed calls went, per phase:

```

```

## Streamed expert cache

Routes to streamed experts go through a device cache
(`src/common/moe_hybrid_expert_cache.cpp`). It keeps a fixed pool of expert
slots on one GPU, laid out as stacked gate, up and down tensors, so a
layer's streamed routes run as one MUL_MAT_ID graph over slot ids, built
like an owner stack (same kernels, same SwiGLU clamp, weighted sum on the
device, one readback) and reused from token to token. Slots are recycled
least recently used first. Misses are loaded by four loader threads, each
copying an expert out of the file mapping into its own pinned buffer and
uploading it on its own stream; a layer queues its misses as soon as it
has routed, so they load while the owners compute.

The slots live on the secondary GPU when there is one. The Strix reads
host memory at about 25 GB/s (0.25 ms per 10.5 MiB expert), while uploads
to the R9700 cross a narrower link (2.1 ms per expert here), so the Strix
is both the cheaper place to land an expert and fast enough to compute a
handful of them per layer.

- `LUCE_EXPERT_STREAM_CACHE_MB`: cache size cap. The cache is sized after
  every other allocation and takes the device's free memory minus its
  headroom (see [Reliability](#reliability)): 481 slots (4.95 GiB) on the
  Strix with the recipe above. A larger value is shrunk to fit. `0` keeps
  the previous uncached path.
- `LUCE_EXPERT_STREAM_DEVICE`: GPU index that holds the slots and computes
  the streamed experts, instead of the secondary (or only) GPU.
- `LUCE_EXPERT_STREAM_PREFETCH=0`: turns off the layer-ahead prefetch below.

While a decode step routes layer L, the same FFN input also goes through
layer L+1's norm and router (selection bias and protected experts
included), in the same graph and the same readback. The streamed experts
that prediction picks start loading behind L's own misses, so they overlap
L's owners and L+1's attention. The prediction only moves bytes early:
L+1 still routes on its own hidden state, and the output does not depend
on it. It names about two thirds of the streamed experts a layer then uses.

The routed-calls line then reports the cache:

```
[deepseek4] decode routed calls: 10800 primary 31.2%, secondary 41.9%, streamed 26.9%; streamed 2907 experts, cache hit 78.3% (prefetched 0.0%), loaded 630 (0 by prefetch) 6.49 GiB: read 476 ms, upload 156 ms, wait 189 ms, compute 261 ms; prefetch accuracy 0.0% of 0
```

`read` and `upload` are summed over the loader threads; `wait` is the time
the decode thread spent blocked on loads. Same recipe with the bias,
protected experts and the usage-ranked placement (warm = second count
request; decode tok/s):

### Warm start

With a usage profile (`LUCE_DS4_HOTNESS_CSV`, or the learned
`LUCE_DS4_ROUTING_STATS_OUT` counts), the cache fills its empty slots after
load with the streamed experts the profile counts most, most used first, in
the background. Loaders take a warm load only while no demand or prefetch
load waits, a warm load never evicts a slot, and warm slots are the first
the LRU recycles, so the fill only moves bytes early and never changes an
answer. The load log reports it:

```
[moe-stream] warm start: 675 of 8942 profiled streamed experts, 19.3% of their routes
[moe-stream] warm start: 675 experts 6.95 GiB in 8221 ms (0.91 GB/s)
```

and the routed-calls line adds `warm X%`, the share of streamed experts a
warm slot served. The fill runs while the server finishes loading (hence
0.91 GB/s) and is done before it is ready. Fused DSpark q=3 recipe, page
cache dropped before the start (decode tok/s; count1 and code are the first
requests of their prompts):

| streamed cache | count1 | count2 | code | code2 |
| --- | ---: | ---: | ---: | ---: |
| cold pool | 4.8 | 21.1 | 10.8 | 24.2 |
| warm start | 5.2 | 21.2 | 12.0 | 24.4 |

All four answers are byte-identical. Only 2% of the first request's
streamed experts hit a warm slot (the profile's top streamed experts are
its least used ones by construction, and the first prefill recycles most
of the pool); most of the gain is the page cache the fill leaves behind:
loader read time drops about 12% on every request. The same holds after
rebasing onto paged concurrent serving (5.2 / 21.1 / 12.0 / 23.3 against
4.8 / 21.0 / 10.9 / 24.3, answers identical); the warm start with paged
attention and several slots is not measured yet.

Two variants were measured and dropped:

- Keeping unused warm slots until nothing else can go raises the warm hits
  to 7% but costs the second request (count2 18.3 tok/s): the pool is
  better spent on what the request just used.
- Reading with `O_DIRECT` (4.5-4.7 GB/s on this drive for 3.5 MB reads
  against 2.4 GB/s for page faults through the mapping) halves the first
  prefill (count1 prefill 5.3 s instead of 10.8 s, code 13.5 tok/s), but
  nothing lands in the page cache, so every recycled expert reads the SSD
  again: count2 6.6 and code2 13.8 tok/s. Direct reads for the warm fill
  alone (6.95 GiB in 1.6 s) lose the page cache the fill otherwise leaves
  and come out slower than the mapped fill.

## Fused hybrid graph

With `LUCE_DS4_FUSED_VERIFY=1 LUCE_DS4_FUSED_HYBRID_DECODE=1` a decode step
and a DSpark verify batch run as one whole-model graph across the R9700, the
Strix Halo and the streamed experts (`ds4_build_fused_verify_graph`), the
graph V4 uses, following the `DeepSeek4Weights` rules: the staggered
pre-mix (`ds4_build_hc_collapse`, no output HC mirror), compressor rows for
every distinct ratio, and the routed experts split over three owners.

Streamed experts are the third owner, computed over the Strix slot cache's
stacks (`MoeStreamedExpertCache::stacks`). Per layer the graph posts its
route ids to host-mapped memory ahead of the secondary branch
(`ggml_host_mailbox_post`) and takes the slot lookup rows right before the
streamed branch (`ggml_host_mailbox_wait`). The cache's resolver thread
(`MoeStreamedMailbox`) answers the layers of a launch in order: it pins the
routed streamed experts, loads the misses and publishes the rows. Each
layer also posts the next layer's routes as predicted from its FFN input
(68-72% of the streamed experts then used), which the resolver prefetches
before blocking on the current layer. Where the wait happens depends on the
GPU driver, see [Reliability](#reliability).

Device routing follows the host rule for protected experts: when a token's
native top-k (without the router bias delta) holds a protected expert, that
selection wins (`ggml_ds4_moe_protected_routes`).

A verify batch runs its attention as one lane per token
(`ds4_fused_attention_lanes`): each lane is the attention core of a decode
step at its position, in position order, over the batch's shared q/kv
projections, so a batch may cross any number of ratio-1/2 compressor
boundaries. HC mixes, the FFN and the head stay batched under batch-invariant
products (MMVQ, and MMVF for F32/F16 up to eight columns), and the FFN joins
as single-token decode does, so every verified token is bit-identical to
fused decode. The graph also returns each token's compressor window row for
rollback.

Recipe: the command of the three-owner section above plus

```bash
export LUCE_DS4_FUSED_VERIFY=1 LUCE_DS4_FUSED_HYBRID_DECODE=1
export LUCE_DS4_TP_ROUTE_PREFORK=1 LUCE_DS4_TP_DEVICE_JOIN=1 LUCE_DS4_TP_DEVICE_JOIN_SPLIT=1
export LUCE_DS4_TP_FUSED_HC_JOIN=1 LUCE_DS4_TP_MAIN_ROUTE_WEIGHTS=1
export LUCE_DS4_TP_COARSE_OWNER=1 LUCE_DS4_TP_NATIVE_ROUTE_WIDTH=1
export LUCE_DS4_TP_MASKED_ROUTES=1 LUCE_DS4_TP_GROUPED_MMVQ=1
export LUCE_DS4_TP_CAPTURE_CACHE_SLOTS=4 LUCE_MOE_FULL_COLD_PARALLEL=1
export GGML_CUDA_BATCH_PEER_COPIES=1 LUCE_CUDA_MMVQ_MOE_ROWS_PER_BLOCK=2
export LUCE_CUDA_I32_REPEAT=1 LUCE_DS4_DIRECT_INDEXER_TOPK=1 GGML_DS4_TOPK_BLOCK_RADIX=1
```

that is, V4's qualified TP set without dynamic route balance (the streamed
owner has no complement) and without `LUCE_MMID_GROUPED`. Measured on the
R9700 + Strix Halo box, usage-ranked placement, page cache dropped before
the start (decode tok/s; code is the first request of its prompt, code2 the
second):

| configuration | count2 | code | code2 |
| --- | ---: | ---: | ---: |
| host path, budget 18000 (before) | 13.9 | 8.6 | 14.9 |
| fused, budget 18000 | 15.8 | 8.1 | 16.9 |

## Concurrent serving (paged)

`--paged-attention --max-concurrency N` (N up to 6) serves V4.1 through
V4's paged path: the sequence engine schedules decode and prompt rows, and
every step runs one gathered fused graph over the rows, each row's attention
as its own lane over its paged history, the FFN batched across rows with the
streamed owner included. On the hybrid tier a prompt advances one token per
step, as for V4.

Every sequence decodes byte-identically to the same request served alone,
whatever the other rows of a step are doing: V4.1 gathered steps run under
batch-invariant products, join FFN partials as single-token decode does, and
pad every row's history to the same buckets whether or not another request
is still prefilling. Readers of a shared compressed cache gather their kv
source's rows and see the row the source emitted for the current token
earlier in the graph.

Measured with the default expert-owner kernels (the TP switches above are
refused with `--paged-attention`, see below), 6 slots, distinct cold
prompts, 128 tokens, device-side mailbox wait:

| concurrent requests | 1 | 2 | 4 | 6 | 8 (2 queued) |
| --- | ---: | ---: | ---: | ---: | ---: |
| aggregate tok/s | 6.9-8.5 | 8.5 | 11.6 | 14.9 | 12.7 |
| per request tok/s | 6.9-8.5 | 7.7 | 4.1 | 3.3 | 3.6 |

All 18 sequences of the N=2 to 8 runs matched their solo runs byte for
byte; with the host-side wait N=2 from a cold page cache also matches
(aggregate 9.9 tok/s on 64-token answers). The single-row step costs about
58 ms warm and 90-220 ms when streamed loads stall, as fused decode does:
the cold prompts are what keeps these numbers low. Warm and shared-prefix
workloads are not measured yet.

## Reliability

- **No device-side wait on the host without CWSR.** The mailbox wait of the
  fused graph was first a kernel spinning on host memory, then a
  `hipStreamWaitValue32`, which rocclr also runs as a polling kernel. With
  compute wave save/restore off (`amdgpu.cwsr_enable=0`, the fleet's setting
  against the R9700 dropping off the bus) a queue with resident waves can
  only be removed once they finish, so a queue eviction while a streamed
  load is slow (a profiler, userptr or SVM restore, another process' memory
  pressure) made the MES fail `REMOVE_QUEUE` and reset the GPU, and twice
  hung the host. The op now reads `/sys/module/amdgpu/parameters/cwsr_enable`:
  with CWSR off the launching thread waits for the answer on the host and no
  wave ever waits (the cost is in the table above), with CWSR on the stream
  wait stays.
- **Headroom.** The streamed expert cache is sized last, after the model,
  the owner stacks, the caches and the drafter, and leaves 4 GiB free on an
  integrated GPU (nothing spills past the carve into shared memory) and
  1.5 GiB on a discrete one. `LUCE_EXPERT_STREAM_CACHE_MB` is a cap and is
  shrunk when it does not fit. At startup the backend logs every device's
  used / total / free memory and refuses a configuration that leaves less
  than the headroom, naming the budgets to lower.
- **Pinned copies only.** Host-device copies of 1 MiB and more go through a
  pinned staging buffer instead of letting the runtime pin the caller's
  pages (on ROCm a pageable transfer registers them as userptr memory, which
  the kernel keeps restoring while the page cache churns under a mapped
  model file).
- **Paged serving with the TP switches.** With `--paged-attention` the
  backend refuses `LUCE_DS4_TP_GROUPED_MMVQ`, `LUCE_MMID_GROUPED`, the
  device-join, peer-copy batching and related TP switches: paged runs with
  them hit the same GPU resets before the causes above were fixed, and they
  have not been requalified since.

## Expert promotion (experimental)

`LUCE_EXPERT_PROMOTE_MB` reserves spare rows on the R9700's owner stacks
(the same count in every layer, allocated with the stacks). A background
worker (`MoeExpertPromoter`) learns each expert's heat from the routes the
fused graph posts to the mailbox and copies experts that turned hot onto
the spare rows (from the Strix owner stack when it holds them, otherwise
from the model file), on its own lowest-priority stream paced to 1 GB/s, at
most one move per 500 ms, demoting the coolest promoted expert when a
challenger is twice as hot. The owner maps change only between graph
launches, so routing never changes, only which owner computes an expert (the
owner sums are grouped differently, so answers can change in near ties).

With 1500 MB (120 rows) a five-turn coding session decodes at 15.2 / 16.1 /
17.0 / 16.4 / 15.5 tok/s against 13.5 / 15.4 / 14.4 / 15.8 / 15.3 without,
but the first requests after start are slower while the rows fill (count2
3.9, code 4.8 tok/s against 17.7 and 10.7), so it is off by default. Next:
fill the rows from the usage profile at load (as the stream cache's warm
start does) instead of while serving, and size the rows per layer by where
the heat is.

## Load between the two GPUs

A kernel trace of fused decode (rocprof, the first request of a session)
shows neither GPU as the limit: the R9700 is busy about 9% of the span and
the Strix computes its owner and streamed experts in under 5% of it, while
the Strix stream spends most of its remaining time waiting for the host to
resolve streamed loads. Balancing expert placement by device bandwidth, or
choosing a device per routed call among replicas, therefore cannot help
before the streamed loads and the per-layer host waits shrink; it becomes
the next lever once they do. The trace under rocprof is also what exposed
the reset above, so the per-layer timeline with the host-side wait still
has to be taken.

## Speculative decoding (DSpark)

V4.1 ships its DSpark draft block in the checkpoint (`mtp.*`: three stages,
128 routed experts top-3, block of five). It runs on the same DSpark loop as
V4 (`LUCE_DS4_SPEC=1`, `LUCE_DS4_DRAFT=<gguf>`).

Convert it from the three safetensors shards that hold `mtp.*` (44-46 of 48
at revision df42c10) plus `config.json` and `model.safetensors.index.json`:

```bash
python3 server/scripts/convert_ds4_dspark_draft_to_gguf.py HF_DIR \
    DeepSeek-V4.1-Flash-DSpark-draft-MXFP4-Q8.gguf \
    --ggml-lib server/build-hip/deps/llama.cpp/ggml/src/libggml-base.so
```

The routed experts are repacked bit-exactly to MXFP4 (the checkpoint's FP4
values and E8M0 scales, 4.25 bits per weight); dense projections go to Q8_0,
router, norms and heads stay F32/F16: 7.4 GiB. The GGUF's arch is
`deepseek41-dflash-draft`, which gives the drafter the same rules as the
target (staggered pre-mix, no per-head query norm, no `output_hc_*`); its
`capture_layer_ids` are 36-38 because the engine captures the residual after
a layer and the reference feeds the residual entering layers 37-39.

The measurements below are on the host hyper-connection path; the fused
graph (above) verifies the same way, faster.

How the verify stays exact. The target runs on the host hyper-connection
path, where a multi-token batch would otherwise be split at every ratio-2
compressor boundary. A V4.1 verify batch instead runs, per layer, one
attention graph (`ds4_run_verify_attention`): the q/kv projections and the
output projection run once for the batch, and every token runs the
single-token decode lane core at its own position, in position order. The
FFN and the output head run once for the batch. All of it runs under
batch-invariant products (`ScopedCudaGraphOverrides`
`mmvq_batch_invariant`): on RDNA4 a multi-column Q8_0 matvec otherwise
uses a different warp split than a one-column one (and at four columns
switches to MMQ), so its columns would not match single-token decode; the
switch keeps the one-column block shape and reads the weights once. F32
router products and ROCMFP2S `MUL_MAT_ID` are already batch-invariant. Every
verified token is therefore bit-identical to plain decode, and greedy output
does not change. Rollback rewinds raw rows and counters as for V4 and puts
back the ratio-2 window rows of the accepted prefix that a later token of
the batch overwrote (`Ds4VerifyWindowRows`).

The drafter attends with the DS4 D=512 flash kernel on HIP. It is faster
than the two F32 BLAS products and, for a drafter on a second GPU, required:
rocBLAS looks Tensile kernels up by name across devices, so a drafter GEMM
on the gfx1151 made the next GEMM of the same name on the gfx1201 target
fail with "no kernel image".

Measured on the box above, the same recipe with the usage-ranked placement,
`LUCE_DS4_PINNED_ROLLBACK=1`, the page cache dropped before each start;
"code2" repeats the code prompt warm. The drafter needs 7.4 GiB: on the
R9700 the expert budget drops from 18000 to 10500 MB.

| plain decode, R9700 budget 18000 | 13.9 | 8.6 | 14.9 | - |

The output of every DSpark row is byte-identical to plain decode at the
same placement. `LUCE_DS4_SPEC_Q` sets the verify width (2 to 6, default
3). Speculation roughly breaks even on this tier: a q=4 verify step costs
about 215 ms against 72 ms for one decode token, because every verified
token still reads its own six routed experts (rarely shared between
consecutive tokens) and runs its own attention lane, and the hybrid tier is
host-bound (the GPUs are busy about 30% of a step: per-layer host
hyper-connections, routing and owner synchronization). A drafter on the
Strix keeps the R9700 budget; its lower code acceptance comes from the text,
not the drafter: that placement answers the code prompt differently (the
count answer, the same text, accepts the same 2.07 drafts), and the drafter's
products and flash attention match across the two GPUs.

## Next targets

Correctness first, then speed.

1. **Engram.** Build a `DeepSeek4EngramRuntime` in the backend, hash the
   step's token ids (prompt tokens, decode history, rollback via the history
   snapshots), read the rows and run `deepseek4_build_engram_apply` on the
   four residual copies entering layers 1 and 14, before their attention HC
   pre. Validate the apply against DeepSeek's `inference/model.py` Engram
   first. Reads are 48 random
   264-byte rows per token (about 13 KB); a row cache and prefetch one step
   ahead keep them off the critical path.
2. **Indexer top-k.** Score the index keys at each index source (query from
   `indexer.attn_q_b`, weights from `indexer.proj`, ReLU, top 512), carry the
   selection to the layers that share it (`idx_src`), and feed it to the
   decode and verify graphs. `build_indexer_topk` generalizes; its first
   scored row and kernel ratio are ratio-4 specific today. Candidate block
   pre-selection only matters above 16,384 compressed rows.
3. **Prefill.** The ratio-2 compressor boundary splits every prefill chunk
   into two-token steps with per-token attention graphs, so prefill is
   linear in prompt length at about 0.6 s per token with a warm page cache.
   A batched ratio-2 / ratio-1 path in `build_compressor_prefill` and V4.1
   support in the layer-major prefill (it needs the staggered pre-mix) are
   the fix.
4. **Decode.** The fused graph runs the three owners in one launch; what is
   left is streamed loads that miss the page cache and, on boxes without
   CWSR, one host wait per streamed layer. Resolving a layer's slots from
   the previous layer's prediction before its post would let most layers
   skip the wait; then the per-layer device timeline decides whether expert
   placement should weigh device bandwidth (see above).
5. **Speculative decoding.** Fused DSpark gains 19-31% over fused decode
   (q=3). Wider verifies stay limited by the per-token streamed experts.
6. **Quantization.** The best V4.1 expert build found so far (MIX10, mixed
   per-layer precision) is not on the test box; ROCMFP2S is what runs today.
7. **Serving.** Paged concurrency is exact; requalify the TP switches with
   it, measure warm and shared-prefix workloads, and bump the snapshot
   format version for V4.1 snapshots.
