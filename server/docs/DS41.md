# DeepSeek V4.1 Flash

DeepSeek V4.1 Flash (`general.architecture = deepseek41`) runs on the
DeepSeek4 backend. This page covers the model files, how to run it on the
Lucebox (R9700 + Strix Halo + SSD), what is supported, and how the port is
laid out. For everything V4 and V4.1 share (hyper-connections, MoE
placement, the hybrid expert tier, reasoning effort, tool calls) see
[DS4.md](DS4.md).

## Model files

| File | Where |
| --- | --- |
| Target, ROCMFP2S (2-bit experts, sign-flip scales) | [`DeepSeek-V4.1-Flash-ROCMFP2S.gguf`](https://huggingface.co/Lucebox/DeepSeek-V4.1-Flash-ROCMFP23-GGUF/blob/main/DeepSeek-V4.1-Flash-ROCMFP2S.gguf) in [Lucebox/DeepSeek-V4.1-Flash-ROCMFP23-GGUF](https://huggingface.co/Lucebox/DeepSeek-V4.1-Flash-ROCMFP23-GGUF) |
| DSpark drafter | built from the `mtp.*` tensors of the [source checkpoint](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash), see [Speculative decoding](#speculative-decoding-dspark) |
| Lucebox placement, router bias, protected experts | `server/share/deepseek41/` (copied next to the binary at build time) |

The ROCMFP2S file is 383 GB: 158 GiB of routed experts, 8 GiB of dense
weights and 189 GiB of Engram tables. The tables are read from the file row
by row and never mapped.

## Running on the Lucebox

```bash
./server/build-hip/luce_server DeepSeek-V4.1-Flash-ROCMFP2S.gguf \
  --profile ds41-lucebox \
  --draft DeepSeek-V4.1-Flash-DSpark-draft-MXFP4-Q8.gguf
```

The `ds41-lucebox` profile (`src/server/launch_profiles.h`) is the measured
recipe: the R9700 as target with 10,500 MiB of experts, the Strix Halo as
`--expert-device hip:1` (its budget is automatic), the Lucebox placement,
router bias and protected experts, dense batched prefill in 4,096-token
chunks, `--max-ctx 131072`, and the fused hybrid decode and verify. Flags on
the command line win over the profile, and environment variables that are
already set keep their value.

Run it as the `lucebox-model` service (root, so the Strix host tier can be
locked) or with `ulimit -l unlimited`: with the default 8 MiB lock limit the
host tier stays empty, the load log says so, and those experts stream from
the SSD instead.

Build as for V4, for example:

```bash
cmake -S server -B server/build-hip -DCMAKE_BUILD_TYPE=Release \
  -DLUCE_GPU_BACKEND=hip -DLUCE_HIP_ARCHITECTURES='gfx1151;gfx1201' \
  -DCMAKE_HIP_ARCHITECTURES='gfx1151;gfx1201'
cmake --build server/build-hip -j --target luce_server
```

## Support

| Piece | State |
| --- | --- |
| Loader: `deepseek41` keys (llama.cpp PR #28696 and DwarfStar dialects), Engram metadata | done |
| Shared compressed caches, ratio-2 / ratio-1 compressors, indexer top-512 | done, tested against `inference/model.py` |
| Engram (layers 1 and 14) on every path, across rollback and snapshots | done, tested against `model.py` |
| Candidate block pre-selection (layer 20) | done (a no-op below 16,384 compressed rows) |
| Three expert owners (R9700, Strix Halo, SSD), router bias, protected experts | done |
| Fused hybrid decode and verify, DSpark speculative decoding | done, bit-identical to plain decode |
| Paged concurrent serving | done, each sequence bit-identical to the request alone |
| Layer-major and dense batched prefill, prefix cache | done |
| Layer split, vision (`--mmproj`), V4 fused decode, F16 verify K/V | refused for V4.1 |
| CUDA builds | refused: on sm_121 the candidate-block selection differs from the reference in `test_v41_indexer_candidates` (6 of 80 queries) |

What still differs from the reference: compressed KV rows stay F16 where
the reference stores FP4, and index scores are F32 where the reference
rounds them to BF16 (near ties can pick another row).

## The Lucebox layout

The routed experts are split three ways:

- **R9700 (primary).** Dense weights, the drafter and the hottest experts.
- **Strix Halo (secondary).** A second expert stack through the in-process
  expert parallel path (`--expert-device`, see DS4.md). The Strix GPU reads
  all of its unified memory at the same speed, so past its carve the stack
  continues in locked host memory (`ggml_backend_cuda_set_host_spill`). The
  host keeps 5 GiB plus one layer-major prefill pass (at most 16,384 prompt
  tokens) free, whatever `--max-ctx` is.
- **SSD (streamed).** Everything else, read on demand into a slot cache on
  the Strix Halo (next section).

Three files decide the split and ship in `server/share/deepseek41/`:

- `--ds4-expert-placement placement_lucebox.json`: JSON `{"owners": [...]}`,
  one of `"primary"`, `"secondary"`, `"stream"` per expert (index
  `layer * n_expert + expert`). Each device keeps what fits its budget and
  demotes the rest one tier; with a routing profile
  (`LUCE_DS4_HOTNESS_CSV`, or counts learned with
  `LUCE_DS4_ROUTING_STATS_OUT`) the least used go first.
- `--ds4-router-bias router_bias_lucebox_40x384_f32.bin`: f32
  `[n_layer][n_expert]`, added once to each layer's selection bias. It
  steers selection toward the R9700 and away from SSD experts (SSD calls
  3.8% -> 0.5% on calibration traffic) without changing mixing weights.
- `--ds4-protected-experts massive_experts.json`: JSON
  `{"<layer>": [expert ids]}`. A token whose unbiased top-k holds a
  protected expert keeps that selection, and protected experts always live
  on the R9700.

The load log prints the result, and every request logs where its routed
calls went:

```
[deepseek4] expert ownership: primary 960 experts 9.89 GiB, secondary 9495 experts 97.80 GiB, streamed 4905 experts 50.52 GiB
[deepseek4] decode routed calls: ... streamed 1635 experts, cache hit 93.4% (prefetched 8.6%, warm 0.0%), loaded 423 (266 by prefetch) 4.36 GiB: read 1476 ms, upload 66 ms, wait 664 ms (157 missed, 104 late), compute 0 ms; prefetch accuracy 80.3% of 1635
```

`missed` counts streamed experts nobody predicted, `late` those whose
prefetch was still loading when the layer needed them.

### Streamed expert cache

`src/common/moe_hybrid_expert_cache.cpp` keeps a fixed pool of expert slots
on the Strix Halo, sized from its free memory after everything else. A
layer's streamed routes run as one `MUL_MAT_ID` graph over slot ids, like an
owner stack. Misses load on four loader threads; while layer L routes, the
graph also predicts layer L+1's experts from the same input and prefetches
them (the prediction only moves bytes early, never the answer). After load,
a usage profile warms the pool in the background. Prompts of 256 tokens or
more load in bulk mode with `O_DIRECT`, so they neither pollute nor evict
the page cache.

In the fused graph the streamed experts are the third owner: each layer
posts its routes to host-mapped memory (`ggml_host_mailbox_post`), a
resolver thread (`MoeStreamedMailbox`) pins and loads them, and the graph
waits for the answer right before the streamed branch.

## Speculative decoding (DSpark)

V4.1 ships its draft block in the checkpoint (`mtp.*`: three stages, 128
routed experts top-3, block of five). Convert it from the safetensors
shards that hold `mtp.*` plus `config.json` and
`model.safetensors.index.json`:

```bash
python3 server/scripts/convert_ds4_dspark_draft_to_gguf.py HF_DIR \
    DeepSeek-V4.1-Flash-DSpark-draft-MXFP4-Q8.gguf \
    --ggml-lib server/build-hip/deps/llama.cpp/ggml/src/libggml-base.so
```

Routed experts are repacked bit-exactly to MXFP4, dense projections go to
Q8_0 (7.4 GiB in total). Pass the file with `--draft`. Verify batches run
each token as its own attention lane under batch-invariant products, so
every verified token is bit-identical to plain decode. `LUCE_DS4_SPEC_Q`
sets the verify width (2 to 6, default 3); q=3 is the fastest on the
Lucebox.

## Prefill, prefix cache and serving

- `--ds4-prefill dense` runs a prompt as batched chunks, and consecutive
  chunks as layer-major passes that read each streamed expert once per
  pass. The default `exact` (token by token) stays the reference.
- With `--prefix-cache-slots N` a chunk also starts at every chat boundary,
  so agent turns restore from the cache (turns 2-5 of a coding session:
  7-13 s to first token instead of about 50 s). A restored turn answers the
  same as a cold run but not always byte for byte.
- The tokenizer matches DeepSeek's control tokens (`<｜User｜>`, `<think>`,
  the tool markers) as whole tokens even when a GGUF types them as normal
  tokens; the load log counts the ones it repaired.
- `--paged-attention --max-concurrency N` (N up to 6) serves V4.1 through
  V4's paged path; the TP tuning switches of the profile are refused with
  it, as they are not qualified there.

## Reliability

- The fused graph waits for streamed layers on the host, never in a GPU
  wave: with compute wave save/restore off (`amdgpu.cwsr_enable=0`) a
  waiting wave made queue evictions fail and reset the GPU.
- The streamed cache is sized last and leaves 4 GiB free on the Strix Halo
  (1.5 GiB on a discrete GPU). At startup the backend logs each device's
  memory and refuses a configuration below the headroom, naming the budget
  to lower.
- Large host-device copies go through pinned staging buffers, freed when
  their thread exits, instead of letting the runtime pin pageable pages.
- Locked host memory is `mlock`ed: the GPU does not mark host pages as
  accessed, so unlocked pages were reclaimed and every swap-in evicted all
  GPU queues of the process.

## What changes from V4 Flash

| | V4 Flash (0731) | V4.1 Flash |
| --- | --- | --- |
| Layers, hidden | 43 (+3 MTP), 4096 | 40 (+3 DSpark), 5120 |
| Routed experts | 256 / top-6, ffn 2048, 3 hash-routed layers | 384 / top-6, ffn 2304, no hash routing |
| Compress ratios | 0, 0, then 4 and 128 alternating | 0, 0, then 2 (layers 2-19), 1 (20-39) |
| Compressed rows | every compressing layer owns its own | kv sources 2, 8, 14, 20 compress; later layers read their rows |
| Indexer | own compressor at every ratio-4 layer | index sources 2, 8, ..., 36; keys from the compressed latent |
| Query norm | per-head RMS norm after `wq_b` | none |
| Hyper-connection pre-mix | own pre coefficients per sub-block | staggered: the previous sub-block's, the head the last FFN's |
| Engram | none | layers 1 and 14, 24 hashed rows per token per layer |

V4 and V4.1 share one backend (`arch_is_deepseek4_family`). The loader
turns every difference into a rule on `DeepSeek4Weights`, and the graph
code tests those rules, never the architecture name; every rule defaults to
V4, so V4 GGUFs run unchanged.

| Rule (`DeepSeek4Weights`) | V4 | V4.1 | Read by |
| --- | --- | --- | --- |
| `attn_q_head_norm` | true | false | `build_mla_qkv_projection`, the DSpark drafter |
| `hc_staggered_pre` | false | true | `ds4_hc_collapse` / `ds4_build_hc_collapse` |
| `shared_index_topk`, `indexer_rotate` | false, true | true, false | `deepseek4_build_indexer_topk`, `Ds4IndexSelectionStore` |
| `kv_src`, `idx_src`, `shared_comp_cache` | every layer its own | sources from `attention.kv_source_layers` / `index_source_layers` | `ds4_comp_cache`, the lane bindings |
| `candidate_source_layer`, `candidate_topk_blocks`, `candidate_block_size` | -1, 0, 0 | 20, 2048, 8 | `deepseek4_candidates.cpp` |
| `engram`, `engram_runtime` | empty | layers 1 and 14 | `deepseek4_engram*.cpp` |
| `compress_ratios` | 0, 0, then 4 / 128 | 0, 0, then 2 / 1 | `build_compressor_step` |
